§ 1系统定位与设计前提

Octop 是面向家庭与小团队的自托管 AI 助手平台：多用户、多 Agent，数据留在自己机器上。一条 octop run 同时拉起三件事——HTTP/WebSocket API、React 控制台，以及 IM 通道与定时任务的后台运行时；全部状态从 ~/.octop/ 下的控制面数据库重建。

它的架构有一个明确且被记录下来的中心决策：单进程，无外部队列。没有 Redis、没有 Celery、没有独立 worker 进程，除用户自己配置的 LLM 供应商之外不依赖任何外部服务。这不是省事，而是 ADR 001 里写明的取舍——面向「pip install && octop init」的自托管用户，多引入一个中间件就等于把运维负担翻倍；而 Agent 调用是秒到分钟级的 I/O 等待，正好落在 asyncio 的甜区。

第二个前提决定了代码的组织方式：Octop 本身不是 Agent 运行时，而是控制面。真正的对话引擎、IM 协议适配、长期记忆、浏览器自动化分属四个独立发布的库，Octop 负责把它们装配进同一个进程，并管理持久状态（用户、Agent 行、供应商、通道、任务、密钥）。

octop-harness
Agent 运行时。基于 LangGraph / deepagents，提供 HarnessAgent、模型路由、工具与技能装载、MCP 加载、对话检查点。Octop 只持有它的句柄。
octop-gateway
IM 桥接。把 10 类平台消息归一成一条入站消息对象，交给 Octop 的处理管线。
octop-memory
分层记忆与全文检索，记忆随工作区迁移；SQLite 或 PostgreSQL 后端。
octop-browser
基于 CDP 的浏览器自动化，支持持久化配置。

前端栈的额外成分

控制台本身相当重：121 个组件文件、60 个 hooks、51 个 API 模块、12 个页面目录（Chat 一域就占 223 个文件）。富内容渲染是它的主要技术负担——react-markdown + KaTeX + Mermaid + react-syntax-highlighter + Monaco 编辑器 + 虚拟列表，另外内嵌 xterm.js 用于浏览器内终端、react-pdf / xlsx / docx-preview 用于文档预览。构建侧为此手写了 manualChunks 分包规则，并刻意关闭标识符压缩以规避 xterm 的压缩期崩溃。PWA 采用手写 Service Worker 策略，且故意不预缓存 index.html，避免 Cache-First 把旧 shell 钉死导致白屏。

§ 3分层与依赖方向

整个后端是四层加一个「外部运行时」带。规则只有一条：依赖只能向内流。传输层可以调领域层，领域层永远不能反向调 HTTP 或 CLI——这条规则由 AGENTS.md 以硬性禁令的形式维护，而不是靠自觉。

§ 4启动链路与运行时装配

启动分成两段：OctopServer.start()（infra/server.py）按依赖顺序装配领域运行时；launch.py 再把 FastAPI 与 uvicorn 挂上去。这个顺序不是随意的——每一步都依赖前一步的产物，而且整体可重启恢复：进程重来时，全部运行态从数据库重建。

  1. 路径与配置。PathLayout.from_env() 定位 ~/.octop（可用 OCTOP_HOME 覆盖）；apply_env_file() 读入 ~/.octop/env；load_config() 按「内置默认 → config.json → OCTOP_* 环境变量」合并。配置 JSON 损坏时直接报错，不会静默用默认值覆盖用户的设置。
  2. 日志。SizeTimedRotatingFileHandler：按天 + 单文件 100 MiB 轮转，保留 14 天，gzip 延迟压缩。
  3. 目录型资产。专家库与子智能体库 refresh() 扫描磁盘目录；PluginManager.seed_bundled() 注入 25 个内置插件后 load_installed()——内置插件默认关闭，按需启用。
  4. 延迟建库（greenfield）。若控制面数据库尚不存在、也没配 OCTOP_DATABASE_*，start() 不打开数据库就返回，把选择权交给首启向导：用户在 /setup/database 决定用 SQLite 还是 PostgreSQL，之后 bind_control_plane() 才真正绑定。已绑定 DB 时，未登录的首个用户会被 setup lockdown 中间件挡住。
  5. 数据库与迁移。open_database() 按 driver 选 SqlitePool 或 PostgresPool；run_migrations() 顺序应用版本号高于当前水位的迁移，随后跑一串幂等的 schema 修复。
  6. 共享服务。build_shared_services() 一次性构造 RepoBundle——26 个 repo 实现，由 SharedServices 以属性透出。这是全进程的持久化入口。
  7. 密钥。JWT 签名密钥走 secret_repo.get_or_create("jwt", lambda: os.urandom(32))，首次启动生成后落库。
  8. 装配运行时（_boot_runtime）。依次构造 AgentManager → TrajectoryStore / HistoryArchive → Gateway（boot() 启动各通道）→ CronDeliveryService → CronManager（boot() 从表里恢复任务，并注册 TLS 自动续期与自动备份两个系统任务）→ ProactiveCareScheduler → UserManager → BridgeManager，最后打包进 AppRuntime 数据类。
  9. 接入 HTTP。build_app() 造 FastAPI 实例，把 server 挂到 app.state.octop_server 作为依赖注入的根，注册中间件与路由，再交给 uvicorn。开了 TLS 时走双监听：HTTPS 主 app + 一个 HTTP companion 应用负责 ACME 质询与跳转。
停止是启动的逆序

stop() 依次关闭 Agently 鉴权 → 主动关怀调度 → Cron → Gateway → Agent 注册表 → UserManager → 历史归档 → 浏览器会话 → 数据库连接。注册表关闭时会先停掉 octop-memory 的 GC 守护线程，否则关 SQLite 时在飞的查询会踩到已释放内存。

中间件的真实执行顺序

Starlette 的语义是后注册的先执行，所以 app.py 里按 bridge_proxy → jwt_auth → setup_lockdown 的次序安装，运行时实际是反过来的：

请求 → setup_lockdown → jwt_auth → bridge_proxy → CORS → 路由
       (无用户时全站 503)  (解 JWT, 挂 request.state.octop_user)

代码注释写明 bridge proxy 必须待在 JWT 内层，因为跨实例转发时已经需要 request.state.octop_user。这是个容易在重构中被无声打破的顺序依赖，值得在改动中间件时盯住。

§ 5并发模型与存储边界

纯 asyncio，线程只作为逃生舱

主进程一条事件循环。项目规则直白：除 run_in_executor 之外不用线程。任何阻塞调用——LDAP 绑定、OAuth 换取令牌、ONNX 推理、子进程等待、备份打包——都要显式丢进 run_in_executor / asyncio.to_thread。这条纪律的直接代价写在 ADR 001 的取舍表里：重 CPU 任务会阻塞事件循环，这也是单进程模型最实的一道天花板。

两处结构化并发值得单独记：AgentManager 为每个 Agent 持一把生命周期锁（串行化 start / reload），又为每个「Agent × 线程」组合持一把执行锁——后者是为了防止 LangGraph 检查点被并发写入交错。批量 reload 则用信号量限流，避免一次性打爆供应商的接口。

两种数据库后端，一个 schema

SqlitePool
单条共享连接 + 一把可重入锁，check_same_thread=False。初始化即设 PRAGMA foreign_keys=ON 与 PRAGMA journal_mode=WAL；事务用 BEGIN IMMEDIATE 而非默认的 deferred，注释说明这是为了躲开 SQLITE_BUSY_SNAPSHOT。首建库在 POSIX 下会 chmod 600。
PostgresPool
psycopg_pool.ConnectionPool，min 1 / max 8。为了让 repo 层只写一套 SQL，池在边界上把 ? 占位符改写成 %s，并用一个兼容行对象让结果同时支持 row["col"] 与 row[0] 两种取值。
单写者假设
ADR 002 明确：同一时刻只有一个活跃的 Octop 写入者，不做多实例写入承诺。SQLite 靠单连接串行化，PostgreSQL 也不提供跨实例协调。

三层存储，互不混淆

ADR 002 划定的三个存储层——最容易混淆、也最需要保持分离的地方
层内容默认位置归属
控制面用户、Agent 行、供应商、通道、定时任务、设置、密钥~/.octop/octop.db 或 PostgreSQLOctop 迁移管理

工作区的内容文件（SOUL、技能、附件）始终是文件，经 BackendWorkspace 读写，从不进数据库。一条硬规则是：Octop 自己的代码不得用 Path.write_text() 直接改 ~/.octop/agents/<id>/——所有工作区内容 I/O 必须走 harness 的 BackendWorkspace，这样本地目录、对象存储与 Docker 沙箱才能共用同一套路径语义。

一个刻意的边界：Octop 的控制面迁移里禁止出现 CREATE EXTENSION。很多托管 PostgreSQL 的角色没有建扩展的权限，而控制面本身也不需要——它只用内置类型。vector 扩展留在 Docker/运维侧，供未来可选的向量检索使用。

调度

进程级只有一个 AsyncIOScheduler，触发器支持 cron: / interval: / date: / agently:（外部邮件事件）四种语法，带 60 秒的 misfire 宽限。时区处理是这里唯一真正的坑：APScheduler 只在传字符串触发器时才注入调度器时区，预构造的触发器会保留自己的时区、否则回落到宿主操作系统时区——所以代码显式把 config.default_timezone 转发进 build_trigger()。这与仓库对外的约定一致：面向用户的日期时间一律用服务端时区，不是浏览器时区。

系统任务（TLS 证书自动续期、自动备份）与用户任务共用一个调度器，但前者登记在 _system_job_ids 里，从数据库恢复任务时会被保留。

§ 6控制面数据库与迁移

迁移是「编号 SQL 对」加「幂等修复函数」的双轨结构。每一版有两份文件——00N_*.sql 给 SQLite，00N_*.pg.sql 给 PostgreSQL，目录下共 20 对 40 个文件，当前 schema 水位是 v20。SQLite 无法用 ALTER 表达的重建（整数主键改造、表重命名）落在 migrate.py 的 _ensure_* / _rebuild_* 助手里，这些助手必须保持幂等，因为它们会在每次启动时无条件再跑一遍。

一个隐式契约

源码里没有 SCHEMA_VERSION 常量。当前版本号由「迁移目录里的最大编号」和「tests/unit/db/test_db_pool.py 里对 v == 20 的断言」共同定义。这是一个可维护性风险点：改迁移编号时，测试是唯一的强制校验，而没有单一常量可以引用。同理，编号 SQL 与 migrate.py 里等价助手的「双轨等价性」完全靠 AGENTS.md 的约定维持，没有自动化的对拍。

§ 7Agent 体系

Agent 是 Octop 的核心实体：一个「模型配置 + 人格 + 工具 + 工作区 + 记忆」的组合，在数据库里是一行，在 harness 里是一个运行中的 HarnessAgent。AgentManager 的职责就是在两者之间保持同步——而它有一条值得注意的设计选择：行数据永远现读数据库，不做进程内缓存。多一次查询换掉一整类缓存失效 bug，对一个以 SQLite 为默认后端的自托管系统来说，这是个划算的交易。

生命周期

boot
构造 harness 侧的管理器（注入供应商配置、Langfuse、团队 peer 回调），然后遍历 agents 表，跳过明确标记为 stopped 的行，逐个启动，单个启动有超时保护，避免一个坏 Agent 拖死整个进程。
create
校验 agent_id（含保留字）→ 配额与后端合法性 → 播种工作区目录 → 写库 → 启动。任何一步失败都走 _abort_incomplete_create() 回滚：摘掉 harness 注册、删目录、删数据库行。支持 defer_bootstrap，把启动挪到后台任务里，让创建接口快速返回。
start / stop
start 只负责「载入 harness 运行时」，不动工作区；stop 先静默 octop-memory 的守护线程再摘除，最后写回 last_state=stopped——这个状态是重启后判断「要不要自动拉起」的依据。
reload
等价于重建 LangGraph 图。批量重载用信号量并发限流；供应商配置变更时只重载受影响的 Agent 集合，而不是全量。

启动一个 Agent 的两段式

第一段 acreate_agent() 把配置交给 harness 建运行时；第二段 _post_start_agent() 做 Octop 侧的补全：注入缺失的网关工具、把工作区自带技能与内置插件技能同步进去、并把过长的 MCP 工具名截断到 64 字符（LLM 的工具名上限），最后注册一个 bootstrap 完成回调，好在下一个 turn 时重建图。团队型 Agent 例外——它不播种工作区、也不同步内置技能。

工作区布局

默认落在 ~/.octop/agents/<id>/。这里有两个容易混淆的维度：root_dir 是 Agent 眼中的 /，workspace_dir 是它的工作目录；两者都由数据库里的值权威决定并原样传给 harness。系统级文件收在 {workspace}/.octop/ 下（会话库、技能与子智能体的系统树、.octop/auth 令牌），这个路径内部固定、不对用户开放配置。

SOUL.md、USER.md、AGENTS.md、MEMORY.md 这套人格文件由 harness 在 bootstrap 时渲染：Octop 把 system_prompt 传进 HarnessAgentConfig，harness 写出文件，之后都从工作区读回。MBTI 人格模板则在 Octop 侧渲染成 {agent_name} / {user_display} / {custom} 三段结构，所以「切换人格」本质上是一次 reload，目的是让 SOUL.md 重新生成。

专家、插件与团队

专家 Experts

装在 ~/.octop/plugins/，包内自带 25 个（weather、qrcode、github-trending、market-quotes…），默认关闭、按需启用。工具名会做非 ASCII 合法化，同时把原名保留进描述，避免中文插件名撑破 LLM 的工具调用格式。
多 Agent 团队 Teams
至少 2 名成员。核心设计是 host 只做调度：它的工具白名单被收窄到 agent_list / ask_agent / memory_search / memory_get / current_time 五个，其余全部进拒绝列表——防止协调者自己动手干活而绕过了委派。成员间通过 harness 的 TeamManager 信箱通信，回复落回父线程的检查点后再推给控制台或 IM。
记忆 Memory
引擎在 octop-memory 外部包里。Octop 侧解析 config_json.memory.backend（SQLite / PostgreSQL / 复用控制面 DSN），并提供一个宿主侧的记忆瘦身协调器，挂在 AgentManager 上做定期裁剪。

§ 8消息网关与对话链路

这是整个系统最值得画出来的一段：Web 控制台、CLI、IM 通道、定时任务四个入口共用一条处理管线。平台差异在进入管线前就被 octop-gateway 抹平了，Octop 侧只有一种入站消息。

几个关键机制

会话键
格式为 agent:channel:subject:chat_type。dashboard 与 cli 是虚拟通道——它们能作为会话来源，但不是 IM 的出站目标。线程本身不记录来源，来源是线程行上的一列，所以「换通道续聊」只是一次行更新。
响应模式
默认 invoke（一次性投递），可选 stream。「折叠」策略会把流式 turn 收成单条回复：工具调用前的文本当作进度旁白丢弃，只留最终文本与媒体——但底层仍然走流式路径，以保住取消、用量与人机确认能力。
流式协议
对话流已从 SSE 迁到 WebSocket，好处是控制台可以在 turn 进行中反向发送斜杠命令或 /compact。唯一保留 SSE 的路径是 HITL 恢复接口。

历史与轨迹是两套并存的记录

不要混淆：面向 UI 回放的归档 vs 面向审计的账本
HistoryArchiveTrajectory
存储独立 SQLite 归档文件控制面表 trajectory_events
结构segments → turns → documents + 内容寻址的 bodies追加型事件流，kind ∈ user / assistant / tool / context / compacted / system
去重文本按 1024 字符切块做 sha256 内部化，引用计数释放无（建库前按体积上限裁剪）
用途UI 分页读取、中断恢复、legacy 迁移轨迹回放与审计
前提仅 SQLite 控制面可用可按 Agent 开关

投影层 projection.py 有一个值得学的细节：它以「最后一条用户消息」为切割点，只取该点之后的消息，并优先采用状态快照而非流式累积的文本。这样既避免了流式重放造成的重复，又不会丢掉那些没有进入状态快照的增量文本。

§ 9其余子系统

认证与首启状态机

密码
Argon2id。策略：≥8 位、同时含字母与数字、不在弱口令字典内、不得与旧密码相同。CLI 与 Docker 引导都遵守同一策略，被拒时 Docker 入口会自动改随机强密码重试。
令牌
JWT / HS256，载荷 {sub, uname, role, iat, exp}，默认 24 小时。密钥 32 字节随机、存 secrets 表。剩余有效期不足 1/3 时签发新令牌，通过响应头 X-Octop-Access-Token 下发给前端做滑动续期。
Setup lockdown
一个安全状态机：当用户数为 0，除 /api/setup/* 与健康检查外全部返回 503 {"setup_required": true}，前端据此跳到安装向导。向导 token 存在内存里（24 字节随机、带 TTL），验证密码接口带 5 次 / 60 秒的限流。
联邦登录
LDAP 用单条 sso_providers.kind='ldap' 配置行，绑定成功即自动开号；SSO 侧支持 OIDC 与可插拔 OAuth（飞书 / 钉钉 / 企微适配器），带 discovery 缓存、PKCE 与一次性 code。登录状态 TTL 600 秒、code TTL 60 秒。
TLS
Let's Encrypt 走 ACME HTTP-01，状态机 PREFLIGHT → CHALLENGING → ISSUING → INSTALLING → RESTART_REQUIRED。证书续期注册为系统级 cron 任务。这一整套依赖 launch.py 的双监听：HTTPS 主应用 + HTTP companion 应用负责应答质询。

连接器与 MCP 网关

内置目录 26 条连接器（腾讯文档、腾讯会议、QQ 邮箱、飞猪、百度地图、携程问道、Notion、OpenAlex、企查查等）。每条声明两种属性：认证方式（personal_token / oauth2 / api_key / imap_app_password / session_cookie …）与 MCP 运行模式。

三种 MCP 模式——决定了工具调用究竟发生在哪里
模式执行位置说明
remote厂商侧harness 直连厂商提供的 MCP URL
gatewayOctop 进程内进程内 Python 适配器，处理厂商私有协议
internalOctop 自托管 HTTPOctop 自己当 MCP server，暴露在 /api/internal/mcp/{kind}/{instance_id}，harness 以 HTTP 方式加载

OAuth 侧实现了 MCP 规范要求的动态客户端注册、授权服务器元数据发现与 PKCE，令牌在过期前 120 秒预刷新。凭据用 Fernet 对称加密（AES-128-CBC + HMAC-SHA256）落库，密钥单独存 secrets。token 型连接器还有一整套 CLI 封装（安装、指纹、运行），因为不少国内服务的「API」实际上是一个命令行工具。

技能与知识库

技能 Skills
可安装到工作区的 SKILL.md 包，来源包括 SkillHub 市场的 HTTP 接口与若干技能站。解压有严格的安全约束（最大字节数、最大条目数、最大解压比），防止 zip 炸弹。
知识库入库
上传 → 多格式解析（md / txt / csv / json / html / pdf / docx / pptx / xlsx）→ 切块（800 字符、重叠 120）→ 向量化（默认本地 ONNX，可切到 OpenAI 兼容接口）→ 索引。
检索
每知识库一个 SQLite sidecar，向量以 struct.pack 存为 BLOB；检索是进程内暴力余弦相似度，默认取 K=8，上下文预算 6000 字符，带引用标注。这里没有用向量索引——sqlite-vec 出现在依赖树里，但它是 LangGraph 检查点组件的传递依赖，与本知识库无关。
OCR
可选后端 rapidocr + onnxruntime + pymupdf，作为 extra 依赖按需安装；图片也可交给视觉模型处理。

工作区存储后端

同一套工作区语义背后可挂 10 种后端：filesystem、shell、postgres、docker、opensandbox，以及对象存储 cos / s3 / oss / obs / 通用 S3 兼容。adapter.py 把数据库行映射成 harness 的后端 spec，resolver.py 展开命名引用与组合树。两个平台特判值得留意：Windows 下默认后端不能用宿主根 /，会改写为 Agent 工作区；PostgreSQL 后端把连接参数拆成离散字段，避免密码里的特殊字符被 libpq URI 误解析。

国际化与可观测性

i18n
只支持 zh 与 en，en 为回退，默认 zh。服务端产出的所有用户可见文案（斜杠回复、IM 状态、API 错误、工具显示名）都必须来自后端 bundle，前端 apiErrors 与后端保持镜像并有测试校验 key 对齐。解析顺序：用户偏好 → 显式覆盖 → 消息元数据 → 通道类型提示（中文平台默认 zh，Telegram 默认 en）→ 默认值。
指标
METRICS 是 5 个进程内计数器（消息总数、流式错误、定时任务运行与错误、活跃 Agent 数），用锁保护、在热路径里惰性 import 以避免循环依赖。刻意保持极简——没有直方图、没有标签维度。
Langfuse
开关与 host / public key 存 settings 表，secret key 存 secrets 表；凭据校验用原始 HTTP 打 Langfuse projects 接口（兼容缺字段的旧自托管版本）。真正的 tracing 在 harness 内部完成，Octop 只负责把配置递进去。

§ 10交付形态与工程化

一个 wheel，五种交付

构建后端是 hatchling，打包配置里显式把已构建的前端产物 src/octop/dashboard/**/* 收进 wheel，并列入 artifacts。这就是「one wheel」的由来：pip install octop 之后，API、CLI、控制台三件事同时到位。

五条交付路径
形态产物要点

Dockerlinux/amd64 + arm64 多架构清单两阶段构建（node 构建前端 → python 运行时）；入口脚本负责首启引导与随机密码

CLI 的三层传输

22 个子命令被明确分到三种执行模型里，每条命令只选一层——领域规则不重复实现：

Offline
只读写本地 ~/.octop 数据库，不起服务。用户、供应商、定时任务的增删改查、模型预设、通道配置等都走这层。
Embedded
进程内起一个短命的 OctopServer，跑完即关。需要 harness 或网关运行时的操作走这层：chats send/repl、cron run-now、agent start/stop/reload、provider test。
External
直接与操作系统或守护进程对话，不经过 Octop 的 HTTP：Ollama 模型管理、扫码绑定（二维码渲染在终端里）、飞书机器人创建子进程。
一个有意的缺失

没有 octop user login。CLI 信任「能读 ~/.octop 就等于有本机权限」这个前提，操作身份靠 --user 或 cli_state.json 里钉住的默认值解析。这是自托管场景下合理的简化，但也意味着 CLI 的权限模型与 HTTP API 的 JWT 模型是两套东西。

CLI 入口本身也做了优化：--help 只读注册表里的短帮助串，不 import 任何子命令模块；另外强制 UTF-8 stdio，专治 Windows GBK 代码页下打印 emoji 与二维码时的编码崩溃。系统服务注册只支持 Linux systemd 与 macOS launchd（ServiceMode = Literal["systemd", "launchd"]）——Windows 侧由安装脚本写启动器。

质量门禁

make all
项目定义的「可以发布」标准：format-all（Ruff 前后端写入）→ lint → typecheck → test（pytest -n auto -m "not live"）。
类型严格度
mypy strict = true 覆盖整个 src/octop，但保留了一份刻意的例外清单：约 12 个路由模块与 api.app 关闭 disallow_untyped_defs，两个 Windows 兼容模块关闭 attr-defined。数据目录与生成的专家库、内置插件被排除在检查之外。
提交钩子
make install-hooks 一次即可（core.hooksPath=.githooks）。钩子跑 make precommit——用 pytest-testmon 只跑受影响的测试以提速——然后再跑一次前端构建。纯文档提交会被识别并跳过。格式化后会把原本已暂存的文件重新 git add，避免工作区与索引漂移。
CI
9 条流水线。ci.yml 只在 PR 上触发，同时跑 ubuntu 与 windows 两套完整非 live 测试，外加一个注入真实凭据的 live 测试作业（缺 secret 自动跳过）。这正是仓库里那些跨平台测试约束的由来：不允许硬编码 POSIX 路径、不允许断言 chmod 位或符号链接语义、落在 OCTOP_HOME 下的测试必须 monkeypatch 环境变量而不是假设 ~/.octop 的字面形状。

分支与发布

feature/* ──PR──► develop ──► release/x.y.z ──PR──► main ──tag v*──► 发布
hotfix/*  ──PR──► main（+ tag）且 ──PR──► develop

规则里防的是历史分叉：禁止把 develop 批量合并进 main，必须经 release/*；release → main 必须用 merge commit 而非 squash；生产标签只能打在合并之后的 main 顶端。每次发版后由 sync-main-to-develop 保证 main 始终是 develop 的祖先。

v* 标签是发布的总开关，一次性触发 PyPI 发布、多架构镜像推送、6 平台桌面包构建，再级联触发飞牛打包与分支同步。由于 GitHub 的 GITHUB_TOKEN 推送不会触发 push 事件，还有一个补充工作流在 release / hotfix PR 合入时自动读取 pyproject.toml 的版本号打标签。

§ 11架构取舍与观察

最后一节是研读中形成的判断，不是官方结论。每条都能在上面的章节里找到依据。

单进程模型的代价是清楚的，也是被接受的

换来什么
  • 零外部依赖：一个进程、一个端口、一份 ~/.octop
  • 重启语义简单——全部运行态从数据库重建，没有外部状态要调和
  • 本地开发与调试路径极短
付出什么
  • 只能垂直扩展，没有 worker 横向扩容
  • 重 CPU 任务会阻塞事件循环——这是靠纪律而非架构避免的
  • 所有写入者共享一个进程，绑定单机

值得注意的是 ADR 001 已经把「未来的拆分层」指了出来——infra/gateway/processor.py 被点名为将来抽出独立 worker 时的天然接缝。也就是说这个架构是为演进留了缝的，而不是打算永远不动。

几个值得关注的点

schema 版本是隐式契约
没有单一常量，靠迁移最大编号与一个测试断言共同定义。改动迁移时缺少编译期或启动期的强校验，是长期维护中最容易出错的一处。
迁移的双轨等价性靠约定
编号 SQL 与 migrate.py 幂等助手必须保持等价，且后者每次启动都会再跑一遍。没有自动对拍，只有文档约束。
核心运行时在包外
对话引擎、IM 协议、记忆、浏览器四个库独立发版。Octop 对它们的耦合是版本号级别的，跨版本升级时需要两侧协同，这在一处便利（职责清晰）与一处风险（联合发布）之间。
知识库检索的规模上限
暴力余弦意味着检索成本随语料线性增长，且全部在进程内完成。对家庭与小团队规模是合适的，但它不是一个能随语料一起长大的设计。
控制台是构建产物
src/octop/dashboard/ 由 npm run build 生成且不入版本库。源码检出后必须显式构建前端才能得到可用界面，否则 octop run 只提供服务端与 API。本次实测确认了这一点。
观测能力刻意最小
5 个计数器加可选的 Langfuse。没有直方图或标签维度，排障主要靠结构化日志与轨迹事件。

这套架构最适合什么场景

Octop 的能力边界与它的取舍高度自洽。当目标是单机自托管、数据自持、多用户共享一组专业 Agent——家庭、小团队、个人开发者——把栈压进一个进程换来的部署简洁性远超它的代价。反过来，如果需要多实例横向扩容、需要独立伸缩的 worker 池、或者语料规模要求真正的向量索引，那么这个架构就是明确不适配的，而且从代码结构看，作者对此有清醒认识。

从工程完成度看，这个仓库最突出的特征不是某个技术选择，而是约束被显式写下来并被工具强制执行：依赖方向有硬性禁令、i18n 键有对拍测试、跨平台行为有专门的测试规范、发布流程有防分叉规则、连 pre-commit 钩子都在格式化后重新对齐索引。对一份 14 万行的代码库来说，这类「把约定变成检查」的投入，往往比架构图上的方框更能决定它三年后的样子。
